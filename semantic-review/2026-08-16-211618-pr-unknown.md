# Atomic media cleanup and at-most-once Telegram dispatch

Delivery-proof deletion now serializes against proof consumption, while banner saves and deletes record attachment or cleanup intent in the same transaction as the CMS mutation. R2 deletion is handled by a leased queue with backoff, a dead state, and an authenticated cron consumer that checks DB RPC results. Telegram moves updates to `dispatching` before a 10-second `sendMessage` call, and courier stats use Tashkent boundaries in SQL. Two P2 edge cases remain in Telegram response classification and client-supplied statistics dates.

Watch for: **[P2, confirmed]** an unreadable Telegram response body can be retried after Telegram accepted the message; **[P2, confirmed]** courier range inputs still use browser-local or UTC dates instead of the Tashkent business date.

**Verdict**: NEEDS_CHANGES

## High-level view

Proof deletion and delivery completion lock the same proof row before moving it out of `verified`; deletion moves it to `delete_pending`, while completion moves it to `consumed`. R2 cleanup then proceeds through durable leased work rather than inside the request.

Banner save and delete RPCs combine the CMS mutation with upload attachment and old-key cleanup enqueueing. The UI and data adapter pass the verified upload identity into this transaction.

Telegram’s `dispatching` state blocks reclaim after a fetch timeout or a successful send followed by failed bookkeeping. **[P2, confirmed]** response-body read and parse failures are instead marked non-ambiguous, making the update claimable even though Telegram may have accepted it.

Courier SQL uses `Asia/Tashkent` defaults and date boundaries. **[P2, confirmed]** the adapter overrides that default with UTC when called without dates, and the current UI sends browser-local dates, so the requested range can differ from the Tashkent business range.

## Proof cleanup is serialized against proof consumption

`queue_delivery_proof_cleanup` locks the proof selected by proof, delivery, and courier identifiers, accepts only `pending`, `verified`, or `delete_pending`, and changes eligible rows to `delete_pending` before enqueueing R2 work. `courier_update_delivery_status` locks the same row and only consumes `verified`; whichever transaction acquires the row first makes the other path reject, so a consumed proof cannot be queued for deletion.

Cleanup claims use `FOR UPDATE SKIP LOCKED`, rotate a lock token, reclaim stale `processing` rows after 15 minutes, back off failed work, and stop after eight claims. Both proof endpoints check the queue RPC error and returned key; the cron handler checks claim and completion errors, while stale-lease recovery handles a failure result that cannot itself be recorded.

## CMS banner media follows the CMS transaction

`save_cms_banner` locks the current banner and verified upload, writes the banner, attaches the upload, and enqueues a replaced key before commit. `delete_cms_banner` enqueues its key before deleting the row. The abandoned-upload cleanup RPC rejects a key referenced by a banner and locks the upload before moving it to `delete_pending`, preventing cleanup from racing successful attachment.

## Telegram response-body failures can re-enter the claim pool

**[P2, confirmed]** `send()` marks only exceptions thrown by `fetch` as ambiguous. It catches `response.json()` rejection and substitutes `{}`, then throws `TelegramSendError(..., false)` because `body.ok` is absent. Body reading can fail after Telegram processed `sendMessage`; the webhook then stores `failed`, and `claim_telegram_update` allows that row to be claimed and sent again. Treat response-body read/parse failure as `ambiguous=true` so it remains in `dispatching` like a timeout or a successful send followed by a failed completion RPC.

## Courier date ranges still depend on the client timezone

**[P2, confirmed]** `get_courier_stats` defaults and `business_day_start` use Tashkent, but `getCourierStats()` supplies `new Date().toISOString().slice(0,10)` when dates are omitted. Between 00:00 and 05:00 Tashkent time that value is the previous date. The current UI supplies its own range using `getFullYear/getMonth/getDate`, which follows the device timezone; a device outside Tashkent can request the wrong month-to-date range. Let PostgreSQL apply its default for default ranges, or format explicit dates in `Asia/Tashkent`.
