# Data-backed storefront catalog, account, and checkout

The storefront now uses the public catalog/CMS and authenticated customer APIs, with client-side routing, realtime refresh, persisted cart/favorites, profile management, and real order submission replacing demo behavior. Catalog records drive cards and product pages, CMS content stays in safe React text/structures, and checkout delegates final pricing and order identity to `create_online_order`. The production build passes, but cart ownership and stock invariants break across session and catalog changes, and several catalog/account states become misleading or stale. Git metadata is absent from the supplied workspace, so this pass could not distinguish added lines from unchanged base lines; findings are limited to the three files identified as intentionally modified and their directly invoked data contracts.

**Watch for:** account cart/favorites copied into anonymous and subsequent accounts on sign-out (**confirmed**); persisted or server quantities remaining above current stock (**confirmed**); one catalog result hidden at tablet widths (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The browser assembles the public catalog and applies search, category, brand, attribute, price, sort, and load-more locally. Two presentation gaps are **confirmed**: category and brand choices use generated ordinal labels instead of database names, and a shared responsive rule hides the fifth catalog result between mobile and desktop breakpoints.

Anonymous cart and favorites are merged into the authenticated account. It is **confirmed** that ending the session writes that merged account state back to anonymous storage for the next visitor/account, while quantities loaded from storage or the account are not reconciled to current stock.

Checkout validates the displayed fields and cart, queries active order-compatible payment methods, keeps one idempotency key per payload, and shows the returned order UUID. It is **confirmed** that direct authenticated navigation can miss the saved profile and default address because the form captures defaults before asynchronous account loading finishes.

CMS values remain text rather than injected HTML, and product SEO uses `textContent` for JSON-LD. History and realtime refresh are connected, but the related-product favorite indicator is **confirmed** to ignore actual favorite state.

<details><summary>Details</summary>

## Cart ownership crosses the sign-out boundary

When `signOutCustomer` clears the session, the merged account cart and favorites remain in component state; anonymous persistence then writes them to `texnobazar.storefront.cart.v1` and `texnobazar.storefront.favorites.v1` (`App.jsx:139-173`, `App.jsx:430`). A later anonymous visitor sees the prior customer's selections, and the next customer has them merged into their server account. This cross-account contamination is **confirmed**. Clear or deliberately partition account-owned state on sign-out, preserving only a pre-login anonymous snapshot if continuity is intended.

## Loaded cart quantities can exceed live inventory

Only interactive updates pass through the stock-clamping `updateCart`. Initial localStorage quantities and quantities merged from `get_customer_account` bypass the catalog cap (`App.jsx:86`, `App.jsx:145-165`), and no reconciliation runs after catalog stock changes. The backend cart RPC caps at 100 rather than `available_stock`, so checkout rejects an overstock cart instead of the cart invariant being maintained. This violation is **confirmed**. Reconcile against the latest catalog after load/refresh and before account synchronization, removing zero-stock lines and capping the rest.

## Catalog controls do not consistently represent results

The catalog groups by `category_id` and `brand_id` but labels them `Kategoriya 1` and `Brend 1` (`App.jsx:313-333`). The ordinal can change with catalog ordering and gives shoppers no entity identity. This requirement gap is **confirmed**; load the public reference rows and label options by real names.

At widths up to 1200px, `app.css` applies `.product-card:nth-child(5){display:none}` globally. The catalog restores the fourth card at the narrower breakpoint but not the fifth, so a counted catalog item disappears from 641px through 1200px. This responsive omission is **confirmed**. Scope teaser-card limits to homepage sections or restore every `.catalog-products .product-card`.

## Account data can arrive after checkout captures defaults

`Checkout` initializes once from `account`, while account loading starts after asynchronous session discovery (`App.jsx:132-140`, `App.jsx:347-348`). On direct `/checkout` navigation or a quick post-authentication transition, later account updates do not populate name, phone, email, or the default address. This stale initialization is **confirmed**. Hydrate untouched fields when account data arrives, or wait for account loading before constructing the form.

## Related favorites display the wrong state

The product page passes `favorites={[]}` to its related `ProductSection` (`App.jsx:337`). An existing favorite therefore renders an empty heart, while `toggleFavorite` consults top-level state and removes it when clicked. This display/action mismatch is **confirmed**. Pass current favorites through the product and related views.

## Security boundary and order submission

CMS and JSON-LD rendering do not introduce an HTML injection path, the payment query is constrained by active-row RLS, and the order RPC independently allowlists methods and reprices lines. The **confirmed** remaining trust-boundary issue is cross-account localStorage persistence: authentication changes need an explicit cart/favorite ownership transition.

## Behavioral coverage is absent

The package has no test files or test script for session transitions, stock reductions, responsive catalog visibility, route restoration, checkout retries, or account hydration. This coverage gap is **confirmed**. Add focused component/integration coverage; the successful Vite build establishes compilation and bundling only.
