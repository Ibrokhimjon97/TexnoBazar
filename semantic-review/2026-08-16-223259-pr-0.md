# Courier distance tracking and performance reporting

This change turns courier GPS points into route distance and exposes the result to couriers, branch managers, and global administrators. It introduces route lifecycle timestamps, a Haversine-based segment filter, tracking/report RPCs, and dashboard surfaces for the resulting metrics. The tracking integrity boundary remains bypassable, delivery-row reuse destroys attempt history, and the client can leave a newly started route untracked.

Watch for: **[HIGH, confirmed]** authenticated couriers can bypass the tracking RPC and forge accepted points; **[HIGH, confirmed]** reassignment after a failed attempt erases the first courier’s outcome and distance; **[MEDIUM, confirmed]** inactive couriers/branches disappear from historical totals; **[MEDIUM, likely]** automatic GPS startup can clear itself before refreshed delivery state arrives.

**Verdict**: NEEDS_CHANGES

## High-level view

`insert_courier_tracking` is not the only tracking write path. The existing authenticated table grant and permissive insert policy let a courier submit arbitrary timestamps and plausible coordinates directly to `courier_tracking`, bypassing the new route-state and accuracy checks.

Performance is derived from the single current `deliveries` row while reassignment reuses that row and resets its route timestamps. A failed attempt can be moved back to ready and assigned to another courier, after which the first courier’s failure and route no longer belong to any report period.

The report seed set contains only currently active profiles and branches. Historical work vanishes from manager and administrator summaries as soon as either dimension is deactivated, and courier self-service returns zero metrics if its branch becomes inactive.

The courier client sets `trackingId` before reloading the just-transitioned delivery. The watcher effect sees the old `picked_up` item and can clear the ID before the refreshed `in_transit` row arrives.

4. **[MEDIUM, likely] GPS auto-start race** — `trackingId` can be cleared while the delivery list still contains the pre-transition status. Refresh or optimistically update the delivery before enabling the watcher and cover the delayed-reload case with a component test.

## Direct table writes bypass the tracking trust boundary

**[HIGH, confirmed]** The migration’s RPC requires an active courier assigned to the order’s branch, ownership of an `in_transit` delivery, and accuracy at or below 1000 m (`supabase/migrations/20260816000000_courier_distance_stats.sql:50-70`). The baseline still grants authenticated users direct `INSERT` on `courier_tracking`, while its RLS policy checks only that `courier_id = auth.uid()`, the profile is active, and some courier role exists (`supabase/migrations/20260101000000_initial_schema.sql:697`, `:750`).

A courier can call the table REST endpoint, target any delivery ID, provide an arbitrary `recorded_at`, and choose low-accuracy values that pass the segment filter. The Haversine speed, jump, and accuracy gates at `supabase/migrations/20260816000000_courier_distance_stats.sql:151-181` cannot distinguish a fabricated plausible route, making manager/superadmin totals attacker-controlled. Revoke direct authenticated insert access and remove the insert policy so client writes must pass through `insert_courier_tracking`; if direct writes remain, reproduce the RPC checks in RLS and prevent client-controlled `recorded_at`.

## Reassignment reuses one delivery row and deletes attempt attribution

**[HIGH, confirmed]** A failed courier transition changes the order back to `processing`; the workflow permits `processing -> ready`, and assignment upserts the same delivery row with a new courier and `assigned_at` (`supabase/migrations/20260113000000_complete_business_workflows.sql:966-970`, `:804`, `:847-852`). The new trigger then clears `in_transit_at` and `completed_at` (`supabase/migrations/20260816000000_courier_distance_stats.sql:27-30`).

The report counts outcomes against only the current `d.courier_id` and filters tracking through the reset route window (`supabase/migrations/20260816000000_courier_distance_stats.sql:108-130`). The original courier loses the failed count and all pre-reassignment distance, while the replacement receives the reused delivery as its assignment. Preserve immutable delivery-attempt rows, or snapshot courier/outcome/start/end per attempt and aggregate tracking against that attempt.

## Active-only dimensions corrupt historical totals

**[MEDIUM, confirmed]** `scoped_couriers` requires both `profiles.is_active` and `branches.is_active` before any delivery or route point can enter the report (`supabase/migrations/20260816000000_courier_distance_stats.sql:99-106`). Deactivating either dimension retroactively removes completed work and distance from arbitrary prior date ranges. The replacement `get_courier_stats` also returns zeros for an otherwise active courier whose branch is disabled.

Build historical report dimensions from deliveries/tracking in the requested period and use activation only for current access checks and new assignments. If inactive rows must be hidden from detail tables, retain them in summary totals and expose an explicit status flag.

## Tracking startup races refreshed delivery state

**[MEDIUM, likely]** After the status RPC succeeds, `transition` sets `trackingId` and only then awaits `load(true)` (`apps/courier/src/App.jsx:24`). Until that request completes, `deliveries` still contains the `picked_up` row. The tracking effect requires a matching `in_transit` row and clears any non-null ID when it cannot find one (`apps/courier/src/App.jsx:19-20`), so a render between the state update and network response disables automatic tracking.

Reload the delivery first and enable tracking from confirmed `in_transit` state, or optimistically update the local status together with `trackingId`. A component test should hold the reload promise open and assert that entering `in_transit` starts exactly one geolocation watcher.
