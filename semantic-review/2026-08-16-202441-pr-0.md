# Telegram, courier, hisobot va CMS workflow xavflari

Source review Telegram boshqaruv hisobotlari, courier delivery yakunlash, admin hisobotlari va CMS media oqimlarida shippingdan oldin tuzatilishi kerak bo‘lgan trust/lifecycle bo‘shliqlarini topdi. Eng katta xavflar Telegram chat link’i aniq sender’ga bog‘lanmasligi, courier istalgan HTTPS URL’ni proof sifatida berishi va biznes kuni hisobotlarining UTC chegaralarida hisoblanishidir. CMS banner va promotion-product oqimlari esa UI’dan oxirigacha ishlamaydi. **Watch for:** **P1 confirmed** Telegram sender binding optional; **P1 confirmed** courier proof R2 obyektiga bog‘lanmagan; **P1 likely** hisobot kunlari DB timezone’da kesiladi; **P1 confirmed** Telegram agregatlari 1,000 savdoda truncation qiladi; **P2 confirmed** webhook claim atomik emas; **P2 confirmed** courier proof upload muvaffaqiyatsiz transition’dan keyin orphan qoladi; **P2 confirmed** banner R2 lifecycle yo‘q; **P2 confirmed** `cms_promotion_products` editor yo‘q.

**Verdict**: NEEDS_CHANGES

## High-level view

Telegram branch/global scope’ni DB role’lari orqali belgilaydi, lekin **P1 confirmed** sender identity bo‘sh qoldirilishi mumkin va **P2 confirmed** update claim unconditional upsert bilan olinadi. Natijada group chat ishtirokchisi link egasining scope’ini ishlatishi yoki bir update parallel qayta ishlanishi mumkin; **P1 confirmed** 1,000 qatorlik cap esa bot ko‘rsatkichlarini jim truncation qiladi.

Courier transition assignee va branch’ni tekshiradi, lekin **P1 confirmed** yakuniy RPC faqat URL sintaksisini tekshiradi. **P2 confirmed** R2 upload transition’dan oldin bajarilgani va pending proof yozuvi yo‘qligi sabab keyingi DB xatosi public orphan obyekt qoldiradi.

Dashboard/report access role va branch bilan cheklangan, ammo **P1 likely** date-only parametrlar DB timezone bo‘yicha `timestamptz`ga cast qilinadi. UTC Supabase’da bu Asia/Tashkent biznes kunini besh soatga siljitadi.

CMS’da **P2 confirmed** banner upload/delete R2 oqimi va **P2 confirmed** promotion-product membership editor mavjud emas. Storefront promotion payload’i join table’ga tayansa ham UI uni to‘ldira olmaydi.

## Telegram chat link sender bo‘lmasa fail-open ishlaydi

**P1 — confirmed.** `save_telegram_chat_link` null `p_telegram_user_id`ni qabul qiladi, `actor()` esa stored qiymat mavjud bo‘lgandagina sender mismatch’ni rad etadi. Bunday group link’da istalgan a’zo `/stats`, `/sellers`, `/orders` va stock query’larni employee branch/global scope’ida ishlata oladi (`supabase/migrations/20260113000000_complete_business_workflows.sql:1693-1747`, `apps/superadmin/api/telegram/webhook.js:6,17`). Table va RPC’da musbat Telegram user ID’ni majburiy qiling, `message.from.id` bo‘lmagan update’ni rad eting va mavjud null link’larni disable/backfill qiling.

## Courier delivery istalgan HTTPS proof bilan yakunlanadi

**P1 — confirmed.** Authenticated courier browser’dan granted `courier_update_delivery_status` RPC’ni to‘g‘ridan-to‘g‘ri chaqira oladi; delivered transition `p_proof_url` uchun faqat HTTPS regex tekshiradi (`supabase/migrations/20260113000000_complete_business_workflows.sql:930-953,1531-1532`). `/api/media/delivery-proof`ni chetlab `https://example.com/a` berish delivery, sale va inventory finalization’ni haqiqiy R2 isbotsiz yakunlaydi. Completed upload’ni delivery ID, key, uploader, MIME va size bilan DB’da saqlang; transition URL o‘rniga proof ID qabul qilib ayni courier/delivery’ga tegishli verified proof’ni atomik consume qilsin.

**P2 — confirmed.** Normal UI avval R2’ga upload qiladi, keyin status RPC’ni chaqiradi (`packages/data/src/delivery.js:11`, `apps/courier/src/App.jsx:24`). Delivery state o‘zgargan yoki sale finalization rezerv topmagan holatda RPC rollback bo‘ladi, public obyekt esa record va delete yo‘lisiz qoladi. Proof’ni pending holatda yozib, consume qilinmagan obyektlar uchun retryable cleanup yarating.

## Hisobot kunlari biznes timezone’da kesilmaydi

**P1 — likely.** Sales, finance, debt, supplier, P&L, dashboard va courier-stat query’lari timestamp’larni `p_from::timestamptz` va `(p_to+1)::timestamptz` bilan solishtiradi (`supabase/migrations/20260113000000_complete_business_workflows.sql:916-917,1320-1417`). Supabase PostgreSQL odatda UTC’da ishlaydi, ilova esa Asia/Tashkent biznes kunidan foydalanadi; natijada local 00:00–05:00 tushib qolib, keyingi kunning shu oralig‘i qo‘shiladi. `p_from::timestamp AT TIME ZONE <branch/business timezone>` orqali start/end UTC instantlarini yarating yoki caller’dan oldindan normalizatsiya qilingan instant qabul qiling.

## Telegram ko‘rsatkichlari 1,000 savdodan keyin noto‘g‘ri

**P1 — confirmed.** `salesData()` `.limit(1000)` qo‘yadi, `/stats` va `/sellers` shu bitta page’ni agregatsiya qiladi (`apps/superadmin/api/telegram/webhook.js:9-11`). 1,001-savdodan boshlab revenue, profit, receipt count va seller ranking ogohlantirishsiz kamayib ko‘rinadi. Branch-authorized aggregate RPC ishlating yoki exhaustion’gacha paginate qiling.

## Telegram update claim duplicate send’ni to‘xtatmaydi

**P2 — confirmed.** Handler row’ni o‘qib, keyin unconditional `processing` upsert qiladi; missing/non-completed row’ni parallel ko‘rgan ikki request ham `sendMessage`gacha boradi (`apps/superadmin/api/telegram/webhook.js:17`). Lookup, claim va completion DB error’lari ham tekshirilmaydi. Claim’ni `INSERT ... ON CONFLICT ... DO UPDATE ... WHERE` va lease/attempt policy’li bitta RPC qiling, ownership natijasini tekshiring va ambiguous Telegram response uchun durable outbox/send state saqlang.

## CMS banner R2 lifecycle’i mavjud emas

**P2 — confirmed.** Banner editor `image_url` va `r2_key`ni qo‘lda kiritadi; upload call yo‘q (`apps/superadmin/src/CmsWorkspace.jsx:5-8`). Presign/complete endpoint’lari faqat `products`, metadata validator esa `products` yoki `delivery-proofs`ni qabul qiladi (`apps/superadmin/api/media/presign.js:18-32`, `apps/superadmin/api/media/complete.js:5-15`, `packages/server/src/r2.js:82-89`). `delete_cms_banner` key’ni qaytarsa ham `deleteCmsRecord` uni tashlab yuboradi (`supabase/migrations/20260113000000_complete_business_workflows.sql:1236-1246`, `packages/data/src/admin.js:17`). Banner-scoped authenticated presign/complete/delete endpoint’lari va retryable R2 cleanup qo‘shing.

## Promotion product membership UI’dan boshqarilmaydi

**P2 — confirmed.** Promotion editor faqat `cms_promotions` maydonlarini saqlaydi; `packages/data/src/admin.js:11-16`da `cms_promotion_products` operation yo‘q (`apps/superadmin/src/CmsWorkspace.jsx:5-8`). Storefront `product_ids`ni faqat join table’dan oladi (`supabase/migrations/20260113000000_complete_business_workflows.sql:1281-1286`), shuning uchun UI’da yaratilgan promotion tashqi DB amalisiz bo‘sh product set bilan qoladi. Product selector va promotion update bilan membership’ni bir transaction’da almashtiradigan authorized RPC qo‘shing.
