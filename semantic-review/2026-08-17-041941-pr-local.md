# Storefront CMS reachability and inventory publish hardening

This pass re-checks the storefront/CMS/inventory publish changes against the prior semantic review. The public CMS boundary, banner placements, partial publish reporting, stale-response guards, filter reset, and ProductCard interaction model have been corrected. The remaining gaps are concentrated in CMS reachability: product hydration silently abandons references beyond the first 100, valid footer/cross-location child menus remain unrenderable, and mobile CMS links route without closing the drawer. These behaviors can make successfully saved CMS configuration appear missing to customers.

Watch for: **[MEDIUM, confirmed]** CMS product hydration marks more IDs attempted than the RPC adapter sends; **[MEDIUM, confirmed]** the builder can save child-menu combinations that no storefront location renders; **[MEDIUM, confirmed]** mobile CMS navigation leaves the drawer open after route changes.

**Verdict**: NEEDS_CHANGES

**Review decision**: CHANGES REQUESTED

## High-level view

The security boundary now uses an explicit storefront settings allow-list in `storefront_cms_payload`, removes the original public CMS/settings policies, revokes direct `anon` table reads, and keeps storefront JavaScript on the RPC path. The prior HIGH finding is resolved in the supplied migration and data adapter.

`home_promo` and `catalog_top` now have customer-facing render paths, while header and explicit mobile roots can render children. Menu reachability is still incomplete because footer children are discarded, the builder permits a child to reference a parent from another location even though the renderer rejects that pair, and internal CMS links in the mobile drawer do not dismiss it.

CMS product references are collected across promotions and product blocks and hydrated independently of the initial catalog page. The adapter truncates each lookup to 100 IDs while the caller marks the entire missing set attempted, so configurations containing more than 100 distinct references permanently omit the remainder for that page session.

Bulk inventory publish now preserves failed IDs, shows each server error, and reloads candidates without allowing stale responses to overwrite current filters. Product listing requests have the same generation guard and reset pagination on filter changes; the product detail and favorite actions are sibling buttons with accessible names.

## Product hydration abandons CMS references after the first 100

**[MEDIUM, confirmed]** `Home` builds one deduplicated set from every promotion and home-block `product_ids`, then marks every missing ID in `hydrationAttempts` before invoking `loadStorefrontProducts` (`apps/storefront/src/App.jsx:402-404`). The data adapter sends only `slice(0,100)` to `storefront_products_by_ids` (`packages/data/src/storefront.js:9`), while the builder offers up to 500 active products and promotion persistence accepts up to 500 IDs (`packages/data/src/admin.js:24`, `supabase/migrations/20260113000000_complete_business_workflows.sql:1404`). Any IDs after the first 100 are neither requested nor eligible for a later retry because they were already marked attempted. Chunk the missing IDs into batches of at most 100 and mark only each submitted batch attempted, or make the adapter perform and merge those batches.

## Builder menu combinations still disappear from every navigation surface

**[MEDIUM, confirmed]** header and explicit mobile roots now render same-location children through `childrenFor`, but `Footer` still filters to root footer items and never renders their children (`apps/storefront/src/App.jsx:386-392, 674-677`). The builder exposes the parent selector for footer items as well as header/mobile items, so a valid saved footer child remains unreachable.

**[MEDIUM, confirmed]** the builder’s parent list includes every root regardless of the child’s selected location (`apps/superadmin/src/CmsWorkspace.jsx`, `CmsEditor` menu fields), while the renderer accepts a child only when its location equals its parent’s location (`apps/storefront/src/App.jsx:389`). Selecting a header parent for a mobile child, or changing location after choosing a parent, produces an active public row that is neither a root nor a child accepted by any renderer. Filter parent choices by location and reset/validate `parent_id` when location changes; either render footer children or prohibit parent selection for footer entries.

## Mobile CMS routes remain covered by the open drawer

**[MEDIUM, confirmed]** mobile root and child CMS buttons call `navigateTarget`, and that function updates history and route state but does not call `setMenu(false)` (`apps/storefront/src/App.jsx:320-328, 392`). The `go` path closes the drawer, so category fallbacks and built-in actions work, but CMS-configured internal links leave the fixed drawer visible over the newly rendered destination. Close the menu as part of `navigateTarget` or wrap every mobile CMS action with a close before routing.
