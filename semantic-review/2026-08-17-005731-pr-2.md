# Repair, atomic exchange, and correction workspaces

This change adds repair intake and lifecycle tracking, turns exchanges into a composed sale-confirmation/return-completion RPC, and introduces an append-only correction workflow surfaced through the manager application. Operational writes are kept behind role-checking `SECURITY DEFINER` RPCs, with repair, exchange, and correction history recorded separately from the original sale. The manager UI adds direct routes for each workflow and adapters for the new RPC contracts. **Watch for: [confirmed] the manager app does not compile; [confirmed] exchange overpayments are recorded but never paid out; [confirmed] correction approval does not freeze the approved reversal; [confirmed] immutable repair costs can be duplicated by retries; and [likely] correction approval provides no maker-checker separation.**

**Verdict**: NEEDS_CHANGES

## High-level view

Repair events and costs are append-only, but cost posting has no idempotency boundary, currency-safe total, or finance-ledger effect. Cancellation also fails to preserve the admitted unit status.

The exchange RPC composes replacement sale confirmation and return completion in one database transaction. When return credit exceeds the replacement total, however, `refund_due` is displayed and stored without any payout method or disbursement record.

Corrections preserve the original sale and create a return/replacement ledger on application. The reversal lines are selected only after approval, while replacement payment is entered earlier without a correction quote, so the approved record does not identify a stable amount or unit set.

The new tables are default-deny to application roles and reached through RPCs that enforce branch roles. The correction state machine nevertheless lets the same POS manager request, approve, and apply a correction, so approval is not an independent authorization control.

Each adapter invocation creates a fresh idempotency key, while server replay does not compare request content. Manager route integration is also blocked by malformed JSX in `CorrectionWorkspace`.

## Correction route cannot be built

**[critical, confirmed]** `apps/manager/src/CorrectionWorkspace.jsx:17`, in the payment-method `<select>` inside `RequestCorrection`, closes `setForm({...form, method: e.target.value})` incorrectly. `npm run build -w @texnobazar/manager` fails with `Expected "}" but found ")"`, so App routing cannot deliver the new manager workspaces until the JSX is fixed and the build rerun.

## Exchange overpayment has no settlement side

**[high, confirmed]** `execute_sale_exchange` calculates `v_refund` when return credit exceeds the replacement total and persists it as `exchange_transactions.refund_due` (`supabase/migrations/20260817000000_repair_exchange_corrections.sql:252-260`). It passes only consumed credit plus customer-to-store settlements into `manager_confirm_sale`, then calls `complete_sale_return`; there is no refund payment method, cash/finance transaction, or payout reference for the excess. `ReturnsWorkspace` shows “Mijozga qaytariladi” but collects no payout details. Add an explicit refund settlement contract and immutable disbursement ledger, and require it to balance `refund_due` in the same transaction.

## Correction approval does not identify the approved reversal

**[high, confirmed]** `apply_business_correction` derives `v_lines` from whatever sale lines remain eligible at application time (`20260817000000_repair_exchange_corrections.sql:305-308`), not from a line-and-amount snapshot stored when the correction is requested or approved. A return completed between approval and application silently changes the units and accounting value being reversed. For replacement corrections, `CorrectionWorkspace` asks for an “exact difference” before that return exists and without a quote endpoint, then forwards the stale payload to `execute_sale_exchange` (`:311`), which rejects any amount that no longer matches. Persist the exact reversal lines, amounts, replacement pending sale, and computed settlement requirements before approval; lock or revalidate that snapshot and expose the same quote to the UI.

## Repair cost history is append-only but not retry-safe

**[high, confirmed]** `add_repair_cost` inserts directly into immutable `repair_cost_entries` and emits an immutable event without accepting an idempotency key (`20260817000000_repair_exchange_corrections.sql:198-208`; `packages/data/src/operations.js:31`). If the commit succeeds but the response is lost, retrying creates a second cost that the application cannot update or delete. Add a caller-stable idempotency key, request hash, and repair-scoped uniqueness constraint; alternatively add an explicit append-only void/correction entry.

## Idempotency keys do not bind to request intent

**[medium, confirmed]** `create_repair_order`, `execute_sale_exchange`, and `request_business_correction` return the row found by `(branch_id, idempotency_key)` without checking that the unit, return, pending sale, reason, payload, location, or settlements match (`20260817000000_repair_exchange_corrections.sql:143-145, 246, 270`). The adapters generate `crypto.randomUUID()` inside each call (`packages/data/src/operations.js:27-34`), and the workspaces do not retain a key across retries. A reused key can report success for unrelated input, while a network retry normally uses a new key and can create another repair/correction request. Follow the existing `request_sale_return` pattern: persist a canonical request hash, reject key reuse with different input, and retain the key for the lifetime of a UI submission.

## Correction approval is not a separate privilege boundary

**[high, likely]** `request_business_correction`, `approve_business_correction`, and `apply_business_correction` all authorize through `require_pos_manager`, and no transition rejects `requested_by = auth.uid()` or `approved_by = auth.uid()`. The same manager can create, approve, and irreversibly apply their own sale reversal despite the requested/approved state model and separate actor columns. If approval is the intended control, require a distinct approver and give approval/application to an explicit higher-trust role such as admin or accountant; otherwise avoid presenting approval as independent oversight.

## Repair costs are not accounting-safe totals

**[medium, confirmed]** `repair_cost_entries.currency` accepts any value cast to `char(3)`, while `list_repair_orders` reports `sum(c.amount)` as one `total_cost` without grouping or conversion (`20260817000000_repair_exchange_corrections.sql:57, 206, 220`). The migration never links repair costs to `finance_transactions`, so these amounts do not enter the existing operating-expense/P&L ledger. Constrain costs to branch currency or aggregate by currency, and either post an immutable finance transaction atomically or label these values as non-accounting estimates.

## Repair cancellation does not restore the admitted state

**[medium, confirmed]** `create_repair_order` accepts units in either `available` or `returned` status (`20260817000000_repair_exchange_corrections.sql:148`), but cancellation always writes `status='available'` (`:189`). Cancelling a repair can therefore mutate a returned unit into ordinary available stock rather than undoing intake. Store and restore the source status, or stop accepting `returned` until its post-repair transition is defined.

## Migration behavior has no executable validation in this workspace

**[medium, confirmed]** No task-specific tests were found for exchange balancing, correction snapshot drift, repair retry behavior, or RPC authorization. `supabase db lint --local --level error` could not connect because local Postgres is unavailable, so the migration was not parsed or exercised against the schema. Add database smoke tests for rollback after nested RPC failures, same-key/same-request and same-key/different-request behavior, overpayment settlement, immutable history, maker-checker authorization, and cross-branch denial.
