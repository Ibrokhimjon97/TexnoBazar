## Delivery proof consume va delete bir xil ownership protokolida emas

**[P1, confirmed]** Courier va superadmin delete endpointlari proof’ni `pending|verified|delete_pending` snapshotidan o‘qib, DB claim/CAS olmasdan `deleteMediaObject()` chaqiradi; keyingi update faqat `id` bilan shartlangan (`apps/courier/api/media/delivery-proof.js:21-24`, `apps/superadmin/api/media/delivery-proof.js:29-32`). Endpoint `verified`ni o‘qigandan so‘ng `courier_update_delivery_status` proof’ni `FOR UPDATE` olib `consumed` qilsa (`supabase/migrations/20260113000000_complete_business_workflows.sql:961-973`), endpoint R2 obyektini o‘chiradi va shartsiz update bilan `consumed → deleted` qiladi. Delete boshida atomik `pending|verified → delete_pending` ownership olish va barcha keyingi transition’larni expected status bilan CAS qilish kerak.

## Cleanup queue durable retry yo‘li bilan tugamaydi

**[P2, confirmed]** `media_cleanup_queue` jadvali va producer upsertlari bor, lekin repo bo‘ylab source qidiruvida queue row’larini lease qiladigan, R2 delete’ni retry qiladigan yoki media row’ni `deleted`ga yakunlaydigan consumer topilmadi (`supabase/migrations/20260113000000_complete_business_workflows.sql:1284-1290`). Vaqtinchalik R2 xatosi `delete_pending` holatini va obyektni cheksiz qoldiradi. Scheduled worker yoki cron bilan chaqiriladigan service endpoint qo‘shilib, delete idempotent va bounded retry’li bo‘lishi kerak.

**[P2, confirmed]** Ikkala proof endpointdagi success/failure update va queue upsert hamda banner endpointdagi mos write’lar Supabase `{ error }` natijasini tekshirmaydi (`apps/courier/api/media/delivery-proof.js:23`, `apps/superadmin/api/media/delivery-proof.js:31`, `apps/superadmin/api/media/banner.js:25`). Shu sabab R2 delete muvaffaqiyatli bo‘lib DB status stale qolsa ham 200, R2 delete va queue persistence ikkalasi muvaffaqiyatsiz bo‘lsa ham 202 qaytishi mumkin. Har bir write tekshirilib, durable cleanup intent saqlanmasa request failure bilan tugashi kerak.

## Banner replacement hali browser-orchestrated saga

**[P2, confirmed]** `deleteCmsRecord('banners')` avval `delete_cms_banner` RPC’da banner row’ni commit qilib o‘chiradi, keyin qaytgan key uchun `/api/media/banner`ni alohida chaqiradi (`packages/data/src/admin.js:18`). Browser yopilishi, token expiry yoki network uzilishi ikki commit orasida yuz bersa, R2 key’ga reference ham, cleanup intent ham qolmaydi. Banner delete va cleanup intent bitta server-side DB tranzaksiyada yozilishi kerak.

**[P2, confirmed]** Replacement yangi key’ni `cms_banners`ga saqlagandan so‘ng attach va old-key delete xatolarini `.catch(console.error)` bilan yutadi (`apps/superadmin/src/CmsWorkspace.jsx:8`). Bu yangi upload’ni `verified`da yoki eski obyektni orphan qoldirib, baribir success UI’ni ko‘rsatadi. Save, attach va eski key cleanup intent server-side replace operatsiyasida durable bog‘lanishi kerak.

## Telegram claim tashqi send’ni idempotent qilmaydi

**[P2, confirmed]** Webhook `sendMessage`dan keyin alohida `finish_telegram_update(..., true)` qiladi; request Telegram’da qabul qilinib response yo‘qolsa yoki send’dan keyin DB finish ishlamasa, catch failed holatini yozishga urinadi va 500 qaytaradi (`apps/superadmin/api/telegram/webhook.js:7,16-17`). `claim_telegram_update` failed row’ni darhol, processing row’ni lease tugagach qayta claim qiladi (`supabase/migrations/20260113000000_complete_business_workflows.sql:1836-1859`), natijada o‘sha javob yana yuboriladi. Dispatch uchun bounded timeout/lease renewal va noaniq accepted holat uchun aniq at-most-once yoki at-least-once siyosati kerak.

## Courier stats defaulti business date’dan oldin tanlanadi

**[P2, confirmed]** `get_courier_stats(p_from date default current_date, p_to date default current_date)` query chegaralarini Tashkent midnight’iga aylantiradi, lekin defaultlarni DB session kalendaridan oladi (`supabase/migrations/20260113000000_complete_business_workflows.sql:909-922`). UTC session’da Tashkent 00:00–04:59 oralig‘ida `current_date` hali kechagi sana bo‘ladi. Defaultlarni `(now() at time zone 'Asia/Tashkent')::date`dan olish yoki parametrlarni majburiy qilish kerak.
