# Repair, exchange, and correction hardening after fixes

The follow-up closes most findings from the prior review: the manager builds, exchange credit is balanced against an immutable excess-refund disbursement, repair cancellation restores its original status, and idempotent writes bind stable keys to request hashes. Corrections freeze reversal lines and settlement amounts and prevent the requester from approving or applying their own correction. Two manager/database contract gaps remain blocking.

**Watch for:** **[confirmed]** correction checkers cannot inspect the frozen scope or settlement before approving it; **[confirmed]** non-UZS branches cannot add repair estimates and their totals are labeled as so‘m; **[confirmed]** the database workflows still have no task-specific executable coverage.

**Verdict**: NEEDS_CHANGES

## High-level view

Exchange execution now splits return value into replacement credit, customer top-up, and excess payout in one transaction, retaining the payout method and reference in an immutable disbursement row. Manager adapters match the new settlement contract, and the production build succeeds.

Correction application consumes stored lines and amounts and rejects scope claimed by another return. The requester cannot approve or apply, but approval itself creates the snapshot, leaving the checker without exact lines, credit, or replacement settlement to inspect beforehand.

Repair submissions retain one UUID across retries, hash mismatches are rejected, and cancellation restores location and status. SQL constrains costs to branch currency and the UI calls them non-P&L estimates, but the browser still submits and renders UZS regardless of branch configuration.

The revoke/grant signatures match the declared RPCs and deny application roles direct table access. No smoke migration covers the new invariants, and local Postgres was unavailable for SQL linting.

## Frozen correction scope is approved before the checker can review it

**[high, confirmed]** `approve_business_correction` computes the lines, return credit, replacement totals, and settlement differences while changing the correction to `approved` (`supabase/migrations/20260817000000_repair_exchange_corrections.sql:307-329`). `CorrectionDetail` exposes only reason and event history in `requested`; snapshot amounts appear afterward and only for replacement corrections (`apps/manager/src/CorrectionWorkspace.jsx:17`). Create a proposed snapshot before approval, show exact lines and amounts for both correction types, and have approval atomically verify and bind that proposal or its hash.

## Repair estimates still assume UZS across the adapter and UI

**[medium, confirmed]** `add_repair_cost` requires `p_currency = branches.currency`, but `addRepairCost` defaults to `UZS` and `RepairWorkspace` supplies no currency (`supabase/migrations/20260817000000_repair_exchange_corrections.sql:219-232`; `packages/data/src/operations.js:31`; `apps/manager/src/RepairWorkspace.jsx:15`). `get_inventory_references` omits branch currency and `formatMoney` always appends `so‘m` (`supabase/migrations/20260106000000_inventory_receiving_qr.sql:69-80`; `packages/ui/src/index.jsx:15`). Non-UZS branches therefore cannot add costs and see totals with the wrong unit. Return currency through the repair contract, pass it to `addRepairCost`, and use a currency-aware formatter while retaining the estimate/non-P&L label.

## New database invariants remain unexercised

**[medium, confirmed]** No task-specific SQL test covers hash mismatch, response-loss replay, payout balancing, snapshot conflicts, distinct actors, status restoration, branch-currency rejection, or RPC ACLs. The manager build succeeds, but `supabase db lint --local --level error` could not connect to Postgres. Add a migration smoke test that invokes the declared signatures under authenticated actors and verifies rollback, balancing, replay, snapshots, authorization, and restoration.
