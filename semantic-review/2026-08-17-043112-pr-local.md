# Serialized CMS menu hierarchy enforcement

The menu hierarchy trigger now acquires one transaction-scoped advisory lock before checking either a parent mutation or a child attachment. **Confirmed:** this closes the previously reported interleaving because every hierarchy write waits for the preceding writer to finish, then rechecks the resulting parent/child state before accepting its own write. Global serialization is an intentional trade-off for rare, admin-only menu writes, and the prior approved storefront, CMS security, publishing, request-ordering, and ProductCard conclusions remain unchanged.

## High-level view

A single advisory-lock key gates inserts and updates that can affect the menu hierarchy. Because the lock is held until transaction completion and acquired before both database rechecks, simultaneous parent mutation and child attachment cannot each validate against the old state and commit an invalid nested-parent or cross-location relationship.

The lock serializes all menu hierarchy writes rather than only writes concerning the same parent. This accepted trade-off reduces write concurrency without affecting reads.

## Parent mutation and child attachment share one transaction gate

`enforce_cms_menu_parent` calls `pg_advisory_xact_lock` with the same constant key before either the parent-side child lookup or the child-side parent lookup (`supabase/migrations/20260823000000_storefront_builder_inventory_publish.sql:166-180`). The lock remains owned through commit or rollback, so a competing hierarchy write cannot validate while the first write is uncommitted.

If a parent mutation enters first, a concurrent child attachment waits and then rejects the moved or newly nested parent. If the child attachment enters first, the parent mutation waits, sees the committed child reference, and is rejected by the parent-side guard. The previously likely race therefore cannot leave both transactions committed with an invalid hierarchy.
