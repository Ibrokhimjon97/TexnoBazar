# Payment attempt and exchange refund hardening follow-up

The follow-up adds a forward migration that enforces one active payment attempt per order/provider, delays online exchange payout attestation until provider confirmation, and strengthens schema compatibility detection and readiness probing. The original active-attempt, fallback, and readiness blockers are addressed without depending on a rewritten historical payment migration. The exchange boundary is corrected, but aggregate completion is not serialized, and duplicate cleanup can terminate the wrong live attempt. **Watch for: [confirmed] simultaneous final provider confirmations can both miss the aggregate threshold and never create the immutable exchange disbursement; [confirmed] migration cleanup can fail an older provider-bound `prepared` attempt while retaining a newer unbound `initiated` attempt.**

**Verdict**: NEEDS_CHANGES

## High-level view

A partial unique index now permits only one `initiated`, `prepared`, or `ambiguous` transaction for each order/provider. Initiation locks the order before looking up or inserting an attempt, so concurrent callers serialize and reuse the same active row even with different idempotency keys.

Exchange completion records cash, card, and bank-transfer residual payouts immediately, while Click and Payme disbursements move to provider confirmation. The final aggregate check uses only a shared exchange-row lock, so concurrent confirmations can each observe an incomplete total and leave the exchange permanently without a disbursement record.

Schema recovery now recognizes structural codes and known PostgREST cache messages rather than generic “does not exist” text. The catalog adapter invokes the legacy RPC only when query, zero-or-one category, default sort, and no brand, attribute, price, or stock constraint can be represented.

Readiness resolves each required function through its exact `regprocedure` signature, checks critical payment and storefront columns, and requires the `20260822` hardening marker. The marker and replacement function bodies are created in the forward migration; historical `20260820000000` retains the old behavior and is superseded rather than relied on as an edited fix.

## Active-attempt reuse is serialized, but migration cleanup prefers recency over provider binding

The active-attempt index covers `(order_id, provider)` while state is `initiated`, `prepared`, or `ambiguous`. `create_online_payment_attempt` locks the order before returning an exact idempotent match, reusing an active same-provider transaction, or inserting, which removes the prior concurrent callback ambiguity.

**[confirmed]** The pre-index cleanup ranks duplicates only by `created_at desc, id desc` and marks every older row `failed`. An older `prepared` transaction already bound to a provider ID can be discarded in favor of a newer unbound `initiated` row; subsequent provider completion is rejected by the callback state machine. Rank provider-bound/prepared attempts ahead of unbound initiated rows, or explicitly reconcile/drain active provider transactions before forcing terminal states.

## Aggregate provider confirmation can miss the only disbursement transition

`execute_sale_exchange` inserts immediate disbursements only for cash, card, and bank transfer. Click and Payme confirmation updates the refund ledger and inserts the immutable disbursement only when all confirmed refunds equal `refund_due`.

**[confirmed]** `confirm_payment_refund` locks each refund and payment independently but acquires only `FOR SHARE` on the common exchange row. Shared locks are compatible: two refunds that jointly satisfy the residual can each omit the other uncommitted update, see a total below `refund_due`, and commit without inserting. Retries cannot repair the omission because each already-confirmed refund returns before recomputing the aggregate. Use `FOR UPDATE` on the exchange before changing refund state and summing, or an atomic deferred finalization mechanism.

## Strict degradation boundary and exact readiness contract

The classifier is limited to enumerated PostgREST/SQL structural codes plus explicit cache/function/table lookup phrases. Catalog fallback refuses multiple categories, brands, attributes, price bounds, stock filtering, and non-default sorting.

Readiness uses `to_regprocedure` for exact callable identities, checks `orders.checkout_token_hash`, `products.description_blocks`, and both payment state columns, and includes `payment_runtime_hardening_version()` with schema version `20260822000000`. The forward migration defines that marker after replacing the affected functions; historical `20260820000000` still contains non-unique attempt creation and immediate online exchange disbursement.

Automated test files remain absent by explicit user constraint and are not a blocker. `supabase db lint --local --level error` could not run because no local PostgreSQL instance was reachable.
