# Click/Payme gateway completion with schema recovery and demo inventory

This change adds server-only Click and Payme checkout/callback handling, persistent payment and refund ledgers, exchange-aware residual refunds, and a capability token for anonymous order payment access. It also introduces a public schema-readiness probe, stale-schema error normalization, limited storefront fallbacks, and editable demo catalog records backed by individually tracked units. Provider authentication, secret isolation, transaction guards, and unit-derived demo balances are handled deliberately, but the payment state model still permits ambiguous concurrent attempts and the exchange ledger can attest a provider payout before confirmation. **Watch for: [confirmed] multiple active attempts for one order are not distinguishable at callback time; [confirmed] Click/Payme exchange disbursements are recorded while refunds are pending; [confirmed] catalog fallback can classify unrelated “does not exist” failures as schema drift and discard filters; [likely] readiness can accept an incompatible overload because it checks names only; [confirmed] no repository-owned tests exercise these state machines.**

**Verdict**: NEEDS_CHANGES

## High-level view

Anonymous checkout is bound to a 256-bit capability stored only as a 48-hour hash, while authenticated owners can use identity. Service credentials remain in server routes, provider callbacks authenticate before database access, and browser roles cannot read payment ledgers.

An initiation idempotency key deduplicates only an exact client retry. A new key creates another active transaction for the same order, while both provider contracts identify only the order; callbacks therefore select the newest initiated row rather than the attempt that opened the checkout.

Click refunds are leased to a cron worker and Payme waits for `CancelTransaction`, but exchange completion also creates an immutable `exchange_refund_disbursements` row immediately. That ledger can claim disbursement while the provider refund remains pending, ambiguous, failed, or awaiting manual action.

Schema recovery offers a constrained legacy catalog/CMS response. Its classifier accepts any message containing “does not exist,” and catalog fallback drops brand, attribute, stock, price, multi-category, and sort constraints, turning some runtime failures into successful but materially different results.

The demo seed does not overwrite existing products, so later admin edits, archival, and publication choices persist. Deterministic inventory units trigger balance recomputation from current unit state, so sales, reservations, transfers, and returns drive real balances rather than static batch quantities.

<summary>Issues (5)</summary>

1. **Indistinguishable active payment attempts** — **[confirmed]** different idempotency keys can create multiple active rows although Click and Payme callbacks carry only the order ID. Enforce one active attempt per order/provider or include and bind an internal attempt identifier.
2. **Premature provider disbursement attestation** — **[confirmed]** exchange completion inserts an immutable Click/Payme disbursement before provider refund confirmation. Link a pending payout to the provider refund and create/confirm the disbursement only after `confirm_payment_refund`.
3. **Over-broad catalog recovery fallback** — **[confirmed]** any “does not exist” text can trigger a legacy request that silently omits requested filters. Restrict classification to structural codes/cache signatures and fail when legacy semantics cannot represent the request.
4. **Name-only readiness check** — **[likely]** an incompatible PostgreSQL overload can satisfy the probe. Verify exact function signatures and critical relation contracts or use an applied-migration ledger.
5. **Missing payment and recovery regression tests** — **[confirmed]** no repository-owned tests execute the gateway/refund state machine, fallback boundaries, readiness contracts, or seed reruns. Add database integration and data-layer tests before shipping.

<summary>Details</summary>

## Order-level checkout identity cannot distinguish concurrent attempts

`create_online_payment_attempt` reuses a row only for the same `(order_id, provider, idempotency_key)` and otherwise inserts a new `initiated` row while no row is `paid`. **[confirmed]** No uniqueness rule or reuse path covers an existing `initiated`, `prepared`, or `ambiguous` attempt. Click exposes the order as `transaction_param`, Payme exposes `account[order_id]`, and both callbacks recover an unbound transaction with `order_id`, provider, active state, and `order by created_at desc limit 1`.

Two separately opened checkouts are therefore indistinguishable. A callback from the first can bind the second internal attempt; two provider transactions can prepare against two rows, while the partial unique index rejects only the second transition to `paid`. For Click, that conflict becomes “Conflicting transaction” after a customer may have completed the second payment flow. Enforce one active attempt per order/provider, or put the internal transaction ID into the provider contract and bind callbacks to it; retries should return the active attempt until it is terminal.

## Exchange refund ledger gets ahead of provider confirmation

`complete_sale_return` leaves Click refunds in `pending` for the worker and Payme refunds in `awaiting_provider` for a callback. **[confirmed]** `execute_sale_exchange` nevertheless inserts `exchange_refund_disbursements` for every positive residual immediately, including Click and Payme. The immutable table has no pending/confirmed state, while the corresponding provider row can later become `failed` or `ambiguous`.

The exchange ledger can permanently record a disbursement while the payment ledger says money is unconfirmed. Create a pending payout linked to `payment_refund_transactions` and attest disbursement from `confirm_payment_refund`, or reserve `exchange_refund_disbursements` for synchronously attested cash/card/bank payouts.

The residual-context fix itself fails closed: `execute_sale_exchange` sets transaction-local amount and method before calling `complete_sale_return`, direct authenticated completion with a replacement sale fails when context is absent, and ordinary returns still allocate the full return amount.

## Legacy catalog fallback can turn faults into broader results

`isSchemaCompatibilityError` recognizes structural codes such as `PGRST202`, `42P01`, `42703`, and `42883`. **[confirmed]** It also accepts every message, detail, or hint containing `does not exist`; `loadStorefrontCatalog` then invokes the legacy RPC with only query, a single category, limit, and offset. Brand IDs, multiple categories, attributes, price bounds, stock-only filtering, and sort order disappear while the call resolves successfully with a warning field.

Narrow fallback eligibility to explicit PostgREST/schema SQLSTATE values and known cache messages. If requested semantics cannot be represented by the legacy RPC, return the database-update error instead of a broader catalog. CMS can return an explicitly degraded empty payload under the same strict structural classification.

## Readiness probe verifies names rather than contracts

**[likely]** The readiness query checks only `nspname` and `proname`; PostgreSQL overloads coexist, so an old or accidental overload can satisfy the probe when the signature PostgREST must resolve is absent. It also cannot detect required table/column contract drift.

Use `to_regprocedure` or `pg_get_function_identity_arguments` for exact callable signatures and add critical relation checks, or derive readiness from an applied-migration ledger. The payment entries should at least verify the exact v2 order, method-list, and provider-refund signatures used by the application.

## Critical payment and recovery paths have no automated regression coverage

**[confirmed]** No repository-owned `.test.*` or `.spec.*` files cover repeated initiation, callback replay, simultaneous provider transactions, refund lease expiry, ambiguous reversal reconciliation, Payme cancellation confirmation, exchange residual allocation, readiness false positives, fallback filter loss, or seed reruns.

Add database integration tests around transaction state and payout confirmation, plus data-layer tests proving fallback occurs only for structural schema failures and never broadens an unsupported filtered request. Workspace builds, JavaScript syntax checks, and focused adapter smoke assertions passed. `supabase db lint --local --level error` could not connect to local Postgres, so the SQL migration was not executed or linted in this review.
