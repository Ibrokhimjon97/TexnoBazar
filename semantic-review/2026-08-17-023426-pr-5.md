# Exchange-aware provider refund allocation

The forward migration limits exchange refund processing to the residual payout rather than the full return credit. Zero-residual exchanges create no provider work, different-method payouts do not reverse the original gateway, and replacement completion requires transaction-local residual context. The earlier double-refund defect is closed for single-method sales, but split-tender ordering can bypass the same-provider full-only check. **Watch for:** **confirmed** a cash/card payment recorded before a matching Click or Payme payment can consume the residual before the gateway row is evaluated, leaving a same-provider residual without provider work or full-only validation.

**Verdict**: NEEDS_CHANGES

## High-level view

`execute_sale_exchange` applies only `v_credit` to the replacement sale, then publishes `v_refund` and the attested payout method for `complete_sale_return`. A zero residual terminates allocation before any payment row is touched, while a different residual method skips reversal of the original Click or Payme payment.

A matching gateway row must pass the existing full-unallocated-balance comparison. However, chronological traversal of all original tenders lets an earlier non-gateway tender exhaust the residual before the matching gateway row runs (**confirmed**).

Replacement completion fails when residual context is absent or invalid. Sale confirmation, return completion, provider work, and exchange-ledger insertion share one database transaction, so an uncaught validation or adapter error rolls the workflow back as a unit.

<details><summary>Details</summary>

## Residual context separates replacement credit from payout

The replacement sale receives `v_credit = least(refund_amount, replacement_total)` as internal `exchange_credit`, while provider allocation starts from `v_refund = greatest(refund_amount - replacement_total, 0)`. A fully consumed return credit therefore creates no `payment_refund_transactions` row.

`exchange_refund_method` gates gateway work. A Click or Payme payment whose provider differs from the attested payout method is skipped; a matching row reaches the full-only guard, which requires the requested residual to equal the payment’s complete unallocated provider balance.

## Split tender can bypass matching-provider enforcement

The loop orders every original `sale_payments` row by `created_at, id` and subtracts each row’s amount from `v_remaining`, including non-gateway rows and skipped nonmatching gateways. `manager_confirm_sale` supports up to ten payment entries, so mixed tender is a production state.

For an original 50 cash + 50 Click sale, a 50 residual attested as Click can encounter cash first, mark cash refunded, reduce the residual to zero, and never evaluate Click. The exchange then commits without a Click refund transaction or proof that the residual equals Click’s full available balance (**confirmed**).

Gateway-attested residuals must select the matching provider before consuming unrelated tenders, or reject an ambiguous mapping. Unrelated payment statuses must not change for a payout attested through the gateway.

## Context enforcement and rollback boundary

A replacement exchange passed directly to `complete_sale_return` fails when `texnobazar.exchange_refund_due` is missing, empty, nonnumeric, or negative. Ordinary returns and non-replacement completion retain the full-return path.

Errors from context validation, the full-only guard, allocation, or later ledger inserts propagate from the RPC and roll back the replacement sale, inventory changes, completed return, refund ledger, payment changes, and provider work. Transaction-local settings are discarded on rollback and explicitly cleared on success.
