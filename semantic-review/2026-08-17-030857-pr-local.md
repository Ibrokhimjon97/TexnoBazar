# Payment attempt cleanup and exchange refund serialization

The final hardening pass resolves the two blockers from the prior review. Migration cleanup now refuses ambiguous provider-bound data and otherwise preserves the attempt most capable of completing, while exchange refund confirmation serializes aggregate finalization on the shared exchange row. The active-attempt, compatibility fallback, readiness, and delayed online-attestation fixes remain in place. **Watch for: no remaining concrete code blockers; automated test files are intentionally excluded from this review.**

**Verdict**: APPROVED

## High-level view

Active payment-attempt cleanup fails closed when an order/provider has multiple active rows already bound to provider transaction IDs. Otherwise, provider binding takes precedence over state, then `prepared` over `ambiguous` over `initiated`, before duplicate rows are failed and the partial unique index is installed.

Provider refund confirmation takes an exclusive lock on the common `exchange_transactions` row before changing confirmation state and calculating the exchange-wide total. Concurrent finalizers therefore queue on the same exchange, while the unique disbursement key provides a second exactly-once guard.

Initiation still serializes on the order and reuses the one active provider attempt. Storefront fallback remains restricted to representable legacy queries, readiness resolves exact function signatures and requires the hardening marker, and Click/Payme disbursements remain deferred until provider confirmation.

## Provider-aware cleanup before active-attempt uniqueness

The preflight query groups active `initiated`, `prepared`, and `ambiguous` rows by order and provider, and raises before mutation when more than one row has a non-null `provider_transaction_id`. **[confirmed]** The migration does not guess between multiple externally live transactions.

Ranking then prefers a non-null provider transaction ID, followed by `prepared`, `ambiguous`, and `initiated`, with recency only breaking ties. **[confirmed]** At most one provider-bound row can reach this path, so it survives ahead of any unbound row; without a bound row, a prepared attempt survives. Lower-ranked rows transition to `failed` under the payment-gateway guard before `payment_transactions_one_active_uidx` is created.

`create_online_payment_attempt` still locks the order, returns an exact idempotent match, or reuses the surviving active attempt after validating hash, amount, and currency. The `(order_id, provider)` partial unique index remains the database backstop for active states.

## Exclusive exchange finalization and exactly-once attestation

`confirm_payment_refund` reaches the exchange through the refund’s return and executes `FOR UPDATE OF et`, making confirmations for different refunds on the same exchange contend on one exclusive lock. **[confirmed]** A later confirmer waits for the earlier transaction, then its subsequent aggregate query receives a fresh `READ COMMITTED` snapshot that includes the earlier committed confirmation.

The confirmer rejects totals above `refund_due` and inserts only when confirmed minor units exactly equal the residual. `exchange_refund_disbursements.exchange_id` is unique and the insert uses `ON CONFLICT(exchange_id) DO NOTHING`, so finalization inserts at most one immutable disbursement.

`execute_sale_exchange` excludes Click and Payme from synchronous payout insertion. **[confirmed]** Their disbursement is created only by `confirm_payment_refund`, with a provider reference, after confirmed refunds exactly cover the exchange residual.

## Compatibility and readiness boundaries remain strict
