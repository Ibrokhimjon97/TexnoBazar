# Task #4 reporting and durable electronic receipt delivery

Task #4 adds authorized report RPCs, browser-generated XLSX workbooks, four report views, sanitized receipt snapshots, and a Resend-backed email outbox. Receipt data is snapshotted before delivery and separated from internal sales data. The affected applications compile, but sender authorization, delivery outcome persistence, chart coverage, and financial calculations leave material correctness and security gaps. **Watch for:** **confirmed** customer accounts can enqueue arbitrary-recipient POS emails; **confirmed** a successful provider send can be recorded as dead after a database failure; **confirmed** several advertised report views render no chart; **confirmed** P&L overstates profit by retaining tax.

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed:** ExcelJS produces real workbooks, but chart data is derived only from dated rows. Inventory, P&L, seller, and product reports therefore have rows while their bar and line views have no usable series; sales and P&L also disagree with the new reports on voided sales and tax treatment.

**Confirmed:** receipt snapshots omit cost, profit, and payment external references and are trigger-protected from mutation. The POS queue function reuses broader customer receipt-read authorization, allowing authenticated customers to select an arbitrary delivery address through a staff-oriented sender API.

**Confirmed:** the service-only outbox uses leases, stable provider idempotency keys, bounded retries, and a terminal ambiguous state. The worker’s error boundary can nevertheless classify an accepted send as dead, and a 2xx provider response without a parseable ID is also treated as a definitive failure.

**Confirmed:** polling masks the recipient but lets the original requester bypass the active-user check, so account deactivation does not revoke status access while a token remains valid.

<details><summary>Details</summary>

## POS email authorization inherits customer read access

**High severity, confirmed.** `can_access_safe_sale_receipt` grants receipt read access to the linked customer as well as staff (`supabase/migrations/20260819000000_task4_reports_receipt_delivery.sql:72-84`). `queue_sale_receipt_delivery` uses that predicate without a sender-specific role check and accepts a caller-supplied email (`supabase/migrations/20260819000000_task4_reports_receipt_delivery.sql:207-212`); every authenticated account can execute it (`:307-310`). A customer linked through `customers.auth_user_id` or `orders.customer_user_id` can call the RPC directly with new idempotency keys and use the company sender to forward receipts to arbitrary addresses. Separate read and send authorization, requiring an active sale-owning seller or explicitly approved staff role for POS delivery.

## Provider acceptance can be downgraded to dead

**High severity, confirmed.** The dispatch loop wraps both `sendReceiptEmail` and `finish(..., 'sent')` in the same `try` (`apps/superadmin/api/receipts/dispatch.js:19-24`). If Resend accepts the email but database finalization fails, the catch classifies the database error as non-retryable and attempts to mark the row `dead`. A successful second RPC then offers a manual retry with a new idempotency key even though the original message was sent. Separate provider classification from persistence; provider acceptance followed by a persistence failure must retain a recoverable same-key state or become operator-visible ambiguous, never dead.

A failed attempt to persist any provider outcome leaves the item `processing`, and stale leases are automatically claimed after 15 minutes (`supabase/migrations/20260819000000_task4_reports_receipt_delivery.sql:267-274`). Provider idempotency limits accepted-send duplication, but persistence errors must not redefine the provider outcome.

## Missing provider IDs are treated as safe failures

**Medium severity, confirmed.** The client suppresses JSON parse failures and accepts a successful response only when `result.id` exists; every other 2xx response becomes non-retryable (`packages/server/src/receipt-email.js:20`). An empty, truncated, or schema-changed 2xx body does not prove rejection. Mark successful HTTP responses without a trustworthy ID as `ambiguous` instead of allowing a later retry with a fresh provider key.

## Aggregate reports have empty bar and line models

**High severity, confirmed.** `buildReportVisualization` creates `series` only from rows with `sold_at`, `occurred_at`, `created_at`, `started_at`, or `posted_at` (`apps/superadmin/src/reporting.js:15,20-28`). Inventory rows, seller aggregates, product aggregates, and the P&L object have none. `ChartView` uses `series` for bar and line, while only pie uses `breakdown` (`apps/superadmin/src/AdminReportsWorkspace.jsx:37-41`), so those reports show no bar data and disable line. Use breakdown data for categorical bars and add time-bucketed RPC output for required line charts, including P&L and inventory history.

## P&L counts collected tax as profit

**High severity, confirmed.** P&L sets sales revenue to `sum(s.total)` and computes gross/net profit without subtracting sales tax (`supabase/migrations/20260113000000_complete_business_workflows.sql:1570-1586`). The schema defines `total = subtotal - discount + tax` (`supabase/migrations/20260101000000_initial_schema.sql:276-280`), while the new seller and product reports calculate `line_total - tax - cost` (`supabase/migrations/20260819000000_task4_reports_receipt_delivery.sql:15-16,38-39`). P&L therefore overstates profit by collected tax. Base profit on tax-exclusive line totals and reconcile all reports to one accounting definition.

## Voided sales remain in the sales report

**Medium severity, confirmed.** The sales RPC filters only by date and branch (`supabase/migrations/20260113000000_complete_business_workflows.sql:1490-1502`), while P&L and the new seller/product RPCs exclude `status = 'void'`. Voided transactions remain in the sales table, charts, KPIs, and XLSX but disappear from related reports. Add the non-void scope or explicitly define and display a consistent gross-versus-net policy.

## Delivery ownership bypasses account deactivation

**Medium severity, confirmed.** Polling authorizes `requested_by = auth.uid()` before reaching `can_access_safe_sale_receipt`, whose path enforces `current_user_active()` (`supabase/migrations/20260819000000_task4_reports_receipt_delivery.sql:232-250`). A deactivated requester with a valid token can continue polling. Require an active actor before ownership and sale-access branches, retaining only the service-role exception.

## Security-critical delivery paths lack regression tests

**Low severity, confirmed.** No test files or scripts cover visualization selection, XLSX formula escaping, sender authorization, lease reclamation, provider ambiguity, or finalization failure; workspace scripts expose builds only (`package.json:10-18`, `apps/superadmin/package.json:7-11`). Add database authorization tests, worker/provider unit tests, and report-model tests for every report/view combination.
