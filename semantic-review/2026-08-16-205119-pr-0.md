# Telegram, delivery-proof, business-date va CMS media hardening — ikkinchi pass

Ko‘rsatilgan sakkizta fix source’dan qayta tekshirildi. Telegram sender binding fail-closed ishlaydi, update claim/finish tokenli lease bilan atomik bog‘langan, daily summary’dagi 1000 qatorlik cap yo‘q va filial scope SQL agregatsiyasigacha uzatiladi. Delivery proof UUID bilan DB yozuviga bog‘langan, reportlar Tashkent yarim-ochiq chegaralaridan foydalanadi, banner upload va promotion product selector oqimlari mavjud. **Watch for:** **[P1, confirmed]** verified proof delete delivery finalization bilan poygalashib consumed obyektni o‘chirishi mumkin; **[P2, confirmed]** cleanup queue consumer’i yo‘q va adapterlar persistence xatolarini tekshirmaydi; **[P2, confirmed]** banner delete/replacement cleanup’i durable server operatsiyasiga bog‘lanmagan; **[P2, confirmed]** courier stats default sanasi DB sessiyasining `current_date` qiymatiga bog‘liq.

**Verdict**: NEEDS_CHANGES

## High-level view

Telegram yo‘li webhook secret, majburiy `message.from.id`, chat+sender binding va service-role RPC’lar bilan fail-closed. Claim token va lease bitta upsert ichida olinadi, stale worker token mos kelmasa finish qila olmaydi; branch link daily sales va boshqa bot query’lariga qo‘llanadi.

Delivery proof upload `pending → verified → consumed` oqimini va yangi UUID RPC signature’ni ishlatadi. **[P1, confirmed]** Delete endpoint avvalgi `verified` snapshot’ga ishonib R2 obyektini o‘chiradi, ayni paytda DB RPC shu proof’ni `consumed` qilishi va delete’dagi shartsiz update bu holatni `deleted` bilan bosishi mumkin.

Business date reportlari `Asia/Tashkent` midnight’lari orasidagi `[from, to+1)` intervaldan foydalanadi. **[P2, confirmed]** `get_courier_stats()` parametrsiz chaqirilganda default `current_date` DB sessiya timezone’idan olinadi; UTC sessiyada Tashkent 00:00–04:59 oralig‘ida kechagi sana tanlanadi.

Banner upload va promotion membership oqimlari mavjud. **[P2, confirmed]** Media cleanup fallback’i queue yozadi, ammo source’da consumer yo‘q va adapterlar Supabase update/upsert `.error`larini tekshirmay 200/202 qaytaradi. **[P2, confirmed]** Banner delete va replacement intent’lari clientdagi alohida chaqiruvlarga bo‘lingan; request uzilsa yoki yutilgan xato yuz bersa R2 obyekt va lifecycle holati tashlab ketiladi.

## Delivery proof consume va delete bir xil holatni egallamaydi

`courier_update_delivery_status` proof’ni `status='verified'` sharti bilan `FOR UPDATE` lock qilib, delivery yakunlangach `consumed` qiladi (`supabase/migrations/20260113000000_complete_business_workflows.sql:962-973`).

**[P1, confirmed]** Courier va superadmin delivery-proof endpointlari proof holatini lock yoki compare-and-set bilan delete ownership’iga o‘tkazmaydi. Ular oldin o‘qilgan `pending|verified|delete_pending` holatidan keyin R2 delete qiladi va DB’ni faqat `id` bo‘yicha `deleted` qiladi (`apps/courier/api/media/delivery-proof.js:21-24`, `apps/superadmin/api/media/delivery-proof.js:29-32`). Shu oraliqda delivery RPC `verified → consumed` qilsa, endpoint public proof obyektini o‘chiradi va consumed audit yozuvini `deleted` bilan bosadi. Delete boshlanishidan oldin atomik `verified → delete_pending` CAS/lock olish va keyingi transition’larni joriy state bilan shartlash kerak.

## Cleanup queue retry mexanizmisiz qolgan

**[P2, confirmed]** `media_cleanup_queue` yaratiladi va banner hamda delivery-proof endpointlari R2 delete xatosida unga upsert qiladi, lekin `apps/**`, `packages/**` va `supabase/**` bo‘yicha source qidiruvida queue’dan claim/consume qiluvchi worker, cron yoki RPC yo‘q. Vaqtinchalik R2 xatosi doimiy obyekt leakiga aylanadi va `delete_pending` yozuvlar yakunlanmaydi (`supabase/migrations/20260113000000_complete_business_workflows.sql:1284-1290`).

**[P2, confirmed]** Ikkala proof endpoint va banner endpoint Supabase `.update()` hamda `.upsert()` natijalaridagi `.error`ni tekshirmaydi (`apps/courier/api/media/delivery-proof.js:22-24`, `apps/superadmin/api/media/delivery-proof.js:30-32`, `apps/superadmin/api/media/banner.js:25`). R2 delete va queue upsert ikkalasi ham muvaffaqiyatsiz bo‘lsa API baribir 202 qaytaradi; R2 delete muvaffaqiyatli, DB update muvaffaqiyatsiz bo‘lsa 200 qaytarib stale holat qoldiradi. Persistence natijalari tekshirilishi va durable queue yozuvisiz request xato bilan tugashi kerak.

## Banner cleanup intent’i client uzilishiga ochiq

**[P2, confirmed]** `deleteCmsRecord` avval `delete_cms_banner` RPC orqali banner row’ni o‘chiradi va keyin alohida `/api/media/banner` so‘rovini yuboradi (`packages/data/src/admin.js:18`). Brauzer yopilishi, token yoki network xatosida DB transaction tugagan bo‘ladi, lekin R2 key na o‘chiriladi, na queue’ga yoziladi. DB delete bilan cleanup intent bitta server-side transactionda yozilishi kerak.

**[P2, confirmed]** Replacement oqimi yangi banner key’ni saqlagandan keyin attach va eski-key cleanup xatolarini faqat console’ga yozadi (`apps/superadmin/src/CmsWorkspace.jsx:8`). UI muvaffaqiyat ko‘rsatgan holda eski obyekt yoki noto‘g‘ri upload lifecycle status qolishi mumkin; attach va replacement cleanup intent server-side save operatsiyasiga qo‘shilishi kerak.

## Courier stats default sanasi business timezone’dan olinmaydi

**[P2, confirmed]** Report query’lari `business_day_start(date)` bilan Tashkent `[start, next-day-start)` intervalini ishlatadi, ammo `get_courier_stats(p_from date default current_date, p_to date default current_date)` default sanani avval DB sessiyasining kalendaridan oladi (`supabase/migrations/20260113000000_complete_business_workflows.sql:914-922`). UTC sessiyada Tashkent yangi kunining dastlabki besh soatida parametrsiz RPC kechagi business day’ni hisoblaydi. Defaultni Tashkent timezone’dan aniqlash yoki parametrlarni majburiy qilish kerak.
