# Data-driven storefront with customer account sync and checkout

The storefront replaces static merchandise and customer placeholders with the public catalog, CMS, authenticated account, and online-order APIs. Catalog filtering, stock-aware cart behavior, CMS rendering, History API routes, SEO metadata, profile/address management, and checkout are composed in a single React application while retaining the existing responsive design. Two account-transition races and the lack of automated regression coverage still leave identity isolation and merge correctness insufficiently protected.

**Watch for:** (**confirmed**) an old `loadCustomerAccount` request can populate a newly active user’s state; (**confirmed**) the initial account merge can overwrite cart/favorite interactions made while its writes are pending; (**confirmed**) `/profile` can briefly offer sign-in before session hydration finishes; (**confirmed**) no storefront tests exercise these transitions.

**Verdict**: NEEDS_CHANGES

## High-level view

Catalog and CMS data are loaded through `@texnobazar/data`, with public category/brand/payment lookups coming from the browser client. Products are normalized into a cost-free view model, client-side search/filter/sort/load-more operates over all fetched pages, and product events trigger a debounced catalog reload. CMS content is rendered as React text/structured nodes rather than injected HTML.

Anonymous cart and favorites remain in local storage, then merge once with the authenticated account after both account and catalog hydration. The one-time marker prevents later product refreshes from replaying the original account snapshot, and stale remote favorites are removed independently with `Promise.allSettled`; however, neither account loading nor the pending merge completion is protected from a concurrent identity or user-state change (**confirmed**).

Checkout queries active public payment methods, validates the required customer and stock fields, reuses an idempotency key for an unchanged failed attempt, and only clears the cart after `submitOnlineOrder` returns a real UUID. Slug routes, popstate handling, canonical metadata, escaped CMS rendering, and text-based JSON-LD cover the requested navigation and SEO surface.

There is no storefront test suite or test script, so the async account and merge behavior is only build-validated (**confirmed**). The production build succeeds, but compilation cannot detect the races above.

## Account hydration is not bound to the active identity

`refreshAccount` starts `loadCustomerAccount()` under the session captured when the callback was created, then assigns the response with `setAccount(next)` without checking that the same user is still active (`apps/storefront/src/App.jsx:125-136`). If user A’s request resolves after sign-out or after user B signs in, A’s account payload can become the current `account`; the merge effect then combines A’s cart and favorites into B’s authenticated account. This is a **confirmed** auth-boundary isolation failure because the request has neither cancellation nor a captured-user comparison before committing. Capture the requested user ID and discard the response unless it still matches the active session, or use an effect-local cancellation token tied to that user.

The initial render gate only remains active while both auth is unresolved and the catalog is loading (`apps/storefront/src/App.jsx:307`). When catalog loading finishes before `getStorefrontSession`, `/profile` reaches the `!session` branch and renders the sign-in prompt (`apps/storefront/src/App.jsx:504`) even though an existing session may still be hydrating. This is a **confirmed** profile hydration gap; keep auth-dependent routes behind `authReady`, then keep authenticated profile content behind account hydration.

## Pending account merge can restore newer removals and quantities

The one-time merge snapshots `cart` and `favorites`, awaits all remote writes, and then unconditionally replaces both local states with those snapshots (`apps/storefront/src/App.jsx:197-206`). A customer can change either collection while those requests are pending; when the merge resolves, its final `setCart`/`setFavorites` restores the older snapshot even though the later interaction was already reflected optimistically. This **confirmed** race is separate from the fixed product-realtime replay: the marker prevents another merge after catalog changes, but it does not stop the first merge completion from clobbering newer mutations.

```
account loads -> merge snapshots favorite=true -> remote writes pending
                                     user removes favorite -> local=false
merge completes -> setFavorites(snapshot) -> local=true again
```

Commit only entries that have not changed since the merge began, or serialize user mutations behind account hydration and then replay them after the initial merge. The same guard must cover server ordering so a late merge write cannot leave the remote account behind the UI.

## Auth/account regressions have no automated coverage

No test or spec files exist under `apps/storefront`, and the package exposes only dev/build/preview scripts. This is a **confirmed** coverage gap for the exact async behaviors that required repeated fixes. Add focused tests for user A-to-B account-load races, sign-out during hydration, mutation during the initial merge, product refresh after merge, stale-favorite deletion failure, structured address round trips, and profile gating; retain the successful Vite build as a separate validation.
