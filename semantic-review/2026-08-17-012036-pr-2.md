# Reviewable correction line snapshots

The correction proposal now freezes human-readable product and unit metadata alongside the return fields that drive application. `CorrectionDetail` presents every frozen line while the request is awaiting approval, including the product name, SKU, serial-or-QR identity, condition, and refund amount. The enriched objects remain compatible with `apply_business_correction` because `request_sale_return` reads only the existing `sale_line_id`, `condition`, and `refund_amount` members and ignores the added JSON members. The manager production build succeeds, and no new material source blocker was found.

**Watch for:** None.

## High-level view

`compute_business_correction_snapshot` now carries `product_name`, `sku`, `qr_code`, `serial_number`, and `unit_id` together with condition and per-line refund. The non-null, unique inventory QR provides a human-recognizable fallback when a serial number is absent.

The enriched line array becomes the approved snapshot and is passed unchanged into `request_sale_return`. That RPC extracts only the three established return fields, so presentation metadata does not alter reversal creation or validation.

## Frozen line scope is visible before approval

The proposal query builds each line from authoritative sale, product, and inventory rows, preserving `sale_line_id` and `unit_id` while adding product name, SKU, QR code, serial number, condition, and exact line total as `refund_amount`. `CorrectionDetail` maps these lines in the `requested` state and displays product name, SKU, `serial_number || qr_code`, condition, and refund amount above the approval action. Because `inventory_units.qr_code` is non-null and unique, a missing serial number does not leave the frozen unit unidentified.

## Enriched JSON remains compatible with return application

`apply_business_correction` forwards `approved_snapshot.lines` directly to `request_sale_return`. The receiver reads `sale_line_id` to resolve the authoritative sale line, `condition` for disposition, and `refund_amount` for the refund; it neither deserializes against a closed shape nor rejects unknown keys. `product_name`, `sku`, `qr_code`, `serial_number`, and `unit_id` therefore remain inert display metadata.
