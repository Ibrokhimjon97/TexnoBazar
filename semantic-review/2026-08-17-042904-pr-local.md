# Menu hierarchy enforcement with a concurrent-write gap

This follow-up verifies the fix for parent-side menu mutations. The builder now rejects moving or nesting a root that has children, and the database trigger applies the same rule to ordinary writes while leaving non-hierarchy edits and valid child reassignment available. The database checks do not serialize a child attachment against a simultaneous parent mutation, so two individually accepted writes can still commit an invalid hierarchy. Previously approved storefront reachability, CMS security, publishing, request-ordering, and ProductCard behaviors are unchanged by this focused fix.

Watch for: **[MEDIUM, likely]** concurrent direct writes can attach a child while the intended parent changes location or becomes a child, bypassing the invariant because the trigger reads do not lock the parent relationship.

**Verdict**: NEEDS_CHANGES

**Review decision**: CHANGES REQUESTED

## High-level view

The builder detects whether the edited item has children and blocks changes to that item’s location or parent until the children are removed. Other fields remain editable, and roots without children plus valid child reassignment continue through the existing validation.

The trigger rejects mutations of a referenced root and still requires a selected parent to be a same-location root. Its independent reads are not protected by row or advisory locks, leaving a race between parent updates and child inserts or reassignments.

Prior approved concerns remain as established in the previous review. The focused superadmin production build succeeds.

## Parent-side guard and valid edit paths

On submit, `CmsEditor` rejects a non-null `parent_id` or a location change when any loaded row references the current item (`apps/superadmin/src/CmsWorkspace.jsx:54`). It still allows label, URL, sort-order, and active-state edits, an unreferenced root to move or become a child, and a child to move to another valid same-location root.

`enforce_cms_menu_parent` performs the corresponding parent-side check before its early return for roots, while retaining same-location/root validation for selected parents (`supabase/migrations/20260823000000_storefront_builder_inventory_publish.sql:169-179`). This closes the reported builder and ordinary direct-write paths.

## Concurrent writes can recreate the forbidden hierarchy

**[MEDIUM, likely]** the parent-side `exists` query and child-side parent lookup are plain reads without a row or advisory lock (`supabase/migrations/20260823000000_storefront_builder_inventory_publish.sql:169-179`). One transaction can see no child and move a root while another sees the old root state and attaches a child; changes to `location` or `parent_id` do not alter the referenced primary key, so the foreign key does not enforce this cross-row invariant. Both transactions can pass and leave the child attached to a different-location or nested parent.

Serialize both sides on the prospective parent ID, acquire locks in a consistent order, and re-check after locking. A database-level concurrency exercise should cover this interleaving.
